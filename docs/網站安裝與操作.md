# 網站安裝與操作

日期：2026-10-01

## 接入方式

本工具是自行部署的反向代理套件。Python 管理設定與 Docker；網站流量交給 Envoy，限流只走同機私有 gRPC。原網站不必改程式或申請雲端 API。

安裝命令見根目錄 README。`init` 預設生成觀察模式，`check` 只驗證設定，不接觸 Docker；`render` 只輸出部署檔；`up` 建置、原生驗證後啟動；`down` 停止本工具容器，不刪原網站或外部網路。

### 來源站位址

| 環境 | 設定 |
|---|---|
| Docker Desktop 主機服務 | `upstream.url: http://host.docker.internal:3000` |
| Colima／Lima 的 macOS 服務 | `upstream.url: http://host.lima.internal:3000`，CLI 加 `--docker-context <context>` |
| 已有容器服務 | `upstream.url: http://wordpress:80` 與 `upstream.network: 既有網路名稱` |
| 其他主機 | 可達的私有位址或 HTTPS DNS 名稱 |

Docker 內的 loopback 屬於容器。Linux 主機服務若只監聽主機的 127.0.0.1，bridge 無法直接連入；優先使用既有容器網路或可由閘道到達的私有介面，避免為接入而公開來源站。

保留現有 TLS/CDN/Nginx 時，把流量指向 SiteGuard 的 loopback 埠；SiteGuard 再連原服務。接入測試成功後才切換實際流量，來源站不可留下能繞過防護的公開入口。工具不會自行更改 DNS 或既有 Nginx。

## 防護設定

以下是範例，不是各網站通用的容量數字：

```yaml
version: 1
name: my-site
mode: observe
listener:
  host: 127.0.0.1
  port: 8088
  forwarded_proto: https
upstream:
  url: http://host.docker.internal:3000
  protocol: http1
  preserve_host: true
hosts: [www.example.com]
policy:
  max_concurrent: 32
  queue_size: 8
  rate_per_second: 100
  burst: 200
  per_ip_rate: 20
  per_ip_burst: 40
  max_body_bytes: 10485760
  request_timeout_seconds: 30
  stream_idle_timeout_seconds: 300
routes:
  - name: expensive
    prefix: /api/reports
    max_concurrent: 4
    rate_per_second: 5
    burst: 10
  - name: websocket
    prefix: /ws
    streaming: true
    max_concurrent: 8
  - name: events
    prefix: /events
    streaming: true
trusted_proxy_cidrs: []
trusted_proxy_hops: 0
```

`forwarded_proto: https` 用於已有 HTTPS 代理在前方的部署；直接明文測試可省略。限制依路徑完整區段匹配，較長規則優先；`/api/reports` 不匹配 `/api/reports-other`。預留並行額度總和必須小於全站額度，其餘留給預設路由。Envoy circuit breaker 有多 worker 競態，不能把此額度視為嚴格的應用程式 semaphore。

觀察模式仍記錄會被限流的決策，但不執行自訂速率、body 與並行限制。協定解析、逾時及代理基本資源防護仍啟用。確認合法流量、上傳與串流沒有異常，並依網站容量調整後，再切 `mode: enforce` 重新 `up`。執行模式中限流程序失效會回 503，恢復後重新接通；這是保護來源站與可用性的明確取捨。

只有前方確實有受信代理時，才填其精確 CIDR；不能只相信任意 X-Forwarded-For，也不能把整個網際網路或所有私有網段列為可信。NAT 共用出口會共用每 IP 額度，需評估合法用戶的速率。

## HTTPS、上傳及串流

一般 HTML、表單、JSON、Cookie、Authorization、轉址與快取沿用 HTTP 語意，Host 預設保留。普通路由先完整緩衝 body 再交給來源站；可調整全站或特定路由的 `max_body_bytes`、`timeout_seconds`。不自動重送請求，避免由代理重複提交交易。

WebSocket、SSE、gRPC 串流及長時間下載須設定 `streaming: true`。這些路由不用完整 request body 緩衝或一般總期限，仍受閒置、速率及並行限制。普通路由拒絕利用 Upgrade 標頭觸發串流旁路。gRPC／明文 HTTP/2 來源用 `upstream.protocol: http2`；HTTPS ALPN 可選 `auto`。

HTTPS 來源會驗證 CA 與設定中的來源站名稱；自簽 CA 設 `upstream.tls_ca_file`，無跳過驗證選項。自行終結入站 TLS 時，填 `listener.tls.certificate` 與 `private_key`，只讀掛載原檔；容器身分必須能讀取私鑰，不會自動放寬權限。現有 TLS 代理仍可負責憑證申請與續期。憑證更新後重新 `up`。

為避免不同解析方式繞過路徑限制，代理會正規化點段、合併重複斜線並拒絕編碼斜線。依賴未正規化原始路徑簽章的網站，須先驗證相容性。

## 維運與回復

```bash
siteguard status
siteguard metrics --format json
siteguard metrics --format prometheus
siteguard logs --service all --tail 100
siteguard up
siteguard rollback
siteguard down
```

管理埠只在容器 loopback，metrics 經 Docker 讀取。存取紀錄保留路由、狀態、耗時、拒絕原因，不記錄 query、Cookie、Authorization、IP 或 body。

更新先建候選與原生驗證，成功版本保留在部署目錄 `.siteguard/`；image 標籤由建置內容雜湊決定。更新失敗保存診斷並嘗試還原上一成功版本。首次部署失敗保留現場供 status/logs 排查，不擅自刪除服務。rollback 不包含外部憑證或來源站資料。

限流配額為單程序，重啟重新建立；多副本目前不共享。IP 記錄有硬上限，額滿的新 IP 共用保守桶，因此可能影響合法新訪客。這些限制不能用「適用所有網站」掩蓋。

## 如何判斷有用

比較正常負載是否增加錯誤、過載時重要請求是否更穩定、被拒絕的合法請求有多少。只降低平均耗時或丟掉更多請求，不能單獨算成功。本機重播工具會保留同一份排程、成功／準時率、重複 POST、漏送與完整原始結果。

本工具不處理已飽和的上游頻寬、不替代帳號授權、交易冪等或資料庫期限。真實網站收益需要其流量與容量證據；工具提供相容的接入方式與可量測防護，不提供無條件的普遍有效保證。
