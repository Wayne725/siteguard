# 應用層資源防護專案可行性評估

日期：2026-10-01

建議保留實驗平台，給核心研究假說兩週的驗證期限，再決定是否投入完整 16 週。現有證據支持「可重播、可核對交易的研究原型」，尚不支持「比既有方法更好的防護策略」。若目標是直接推出通用防護產品，目前不建議沿此範圍投入。

知識庫連結：[[原型建置與驗證]]、[[測試操作指南]]、[[_索引]]。

## 問題描述

本次評估專案的改進空間、可用性及繼續投入的價值。依專案計畫，以 16 週、3～5 人的資安專題為主要情境；未假定已有真實客戶或指導老師認可的創新要求。

核心需求應是「後端資源吃緊時，在可接受的報表損失下，維持正常交易準時且正確完成」。Envoy、Python RLS、動態限流及取消訊號都是可能的手段，每一項都需證明有必要。

採第一性原理檢查需求，再核對原始結果與實作。評估分開處理工程正確性、策略效果、研究新穎性及產品採用價值，避免用其中一項代替其他項。

## 解法思路

先做刪除測試：拿掉自訂回饋 RLS，目前五組測試中的正常訂單仍然全部準時完成，正常報表反而保留更多。這只能說明在已測條件下尚無新增控制器的必要性，不能證明所有負載都不需要它。

| 假設 | 已知證據 | 判斷 |
|---|---|---|
| 取消後殘留工作已造成重要損害 | PostgreSQL 報表探針只有 10 次取消，觀察斷線後最長清理 3.858 ms；訂單兩輪均 5/5 | 尚未證明 |
| 新控制器改善正常訂單 | 五組全為 26/26；feedback 全程 2/s | 沒有觀察到增益，也未測到調速效果 |
| 限制報表能保護正常使用者 | 全部使用者共用路由桶；正常報表完成率明顯下降 | 目前是功能間取捨，沒有同功能使用者公平性 |
| 已可當通用產品部署 | 單 app、單 RLS、合成負載、需接入後端狀態 | 適合隔離研究，產品接入價值待驗證 |
| 實作動態限流即有創新 | Envoy 與 Netflix 已有自適應並行及流量分組機制 | 創新須來自可證明的額外訊號價值或新測試方法 |

最後一項依據 [Envoy adaptive concurrency 官方文件](https://www.envoyproxy.io/docs/envoy/v1.39.1/configuration/http/http_filters/adaptive_concurrency_filter) 與 [Netflix concurrency-limits 原始專案](https://github.com/Netflix/concurrency-limits)。Envoy 依完成請求延遲調整並行；Netflix 也提供按流量類型分配額度的做法。這些來源證明已有相關機制，並不直接證明本專案沒有任何研究貢獻。

## 已核對的研究證據

五組均為 PostgreSQL、mixed、seed 42、30 秒整合短測，訂單期限為 1000 ms。

| 組別 | 正常訂單準時完成 | 正常報表完成 |
|---|---|---|
| 共同硬上限 | 26/26 | 7/7 |
| Envoy adaptive | 26/26 | 7/7 |
| adaptive 加 RLS bypass | 26/26 | 7/7 |
| adaptive 加固定 RLS | 26/26 | 2/7 |
| adaptive 加回饋 RLS | 26/26 | 1/7 |

來源為 [原型驗證紀錄](../docs/原型驗證紀錄.md) 及 [原始比較資料](../artifacts/comparison-20261001-101429-473000/comparison.html)，已與各組 summary.json 及 RLS 日誌核對。

這輪最重要的結果是「策略增加了正常報表拒絕，但沒有證明訂單改善」。不能把 1/7 與 2/7 解讀為動態演算法較差，因為 [回饋日誌](../artifacts/comparison-20261001-101429-473000/adaptive-rls-feedback/rls_logs_after.json) 中速率始終為 2.0/s。也不能根據 26 筆成功請求的 p95 小幅下降宣稱優越。

還有三個更根本的設計缺口：

1. **取消實驗尚未形成資源競爭。** 探針把報表排在 0.05、0.55 秒等時點，訂單排在 0.25、1.25 秒等時點。本次 PostgreSQL 探針的 wait 與 cancel 各 15 筆完整 DB 工作區間中，訂單與報表的執行重疊均為零。因此兩輪 5/5 不能證明在取消後資源競爭下仍可保護訂單。來源：[探針時程](../local_ddos_lab/cancellation_probe.py)、[wait events](../local_ddos_lab/results/cancellation-20261001-102014-7552bc69/wait/events.json)、[cancel events](../local_ddos_lab/results/cancellation-20261001-102014-7552bc69/cancel/events.json)。
2. **取消觀察沒有策略對照。** 目前保存的 PostgreSQL 取消探針是 Envoy adaptive 的 wait/cancel 比較；沒有在同一取消負載下比較 fixed 與 feedback，也未同步收集該探針的 Envoy 控制軌跡。取消是否造成取樣偏差、偏差是否造成損害、回饋是否能改善，仍是三個不同的待證命題。來源：[探針編排](../local_ddos_lab/cancellation_probe.py)。
3. **換 seed 不等於改變到達時間分布。** 目前流量使用固定間隔，seed 只影響功能、商品與 ID；正常與額外需求會有固定重合時點。固定相位可能影響共用 token bucket 的搶額度結果，這是需要排除的解釋，尚未證實是報表差異的原因。來源：[make_schedule](../local_ddos_lab/experiment.py)。

3.858 ms 是伺服器觀察斷線後的清理時間，未包含發現斷線前的延遲，不是完整取消成本。RLS 約每次 HTTP 輪詢後等待 250 ms，控制最多每秒更新一次；短暫殘留可能完全沒被快照取到。應優先量測窗口累積占用時間及完整事件關聯，不能用取消次數充當資源成本。

[Envoy v1.39.1 原碼](https://github.com/envoyproxy/envoy/blob/v1.39.1/source/extensions/filters/http/adaptive_concurrency/adaptive_concurrency_filter.cc) 確認未完成編碼的請求在 onDestroy 取消延遲取樣。這是可驗證的設計行為；要稱為有影響的限制，仍須補上後端工作、控制器決策與業務結果的因果證據。

## 可用性與改善順序

| 優先序 | 現況與影響 | 建議 |
|---|---|---|
| 最高 | 核心假說未受有效對照測試，繼續開發容易累積沉沒成本 | 先做兩週去留驗證，暫緩 AI、完整電商、多節點及 UI 大改 |
| 高 | 尚未比較更簡單的後端報表並行額度 | 增加單獨的後端 fixed 組，在相同 PostgreSQL、取消語意及硬上限下校準；確認 RLS 是否提供額外價值 |
| 高 | `/health` 恆回 `ready: true`，Compose 只檢查此端點 | 區分存活與就緒，讓 DB 故障可見；驗收仍以實際 API 與交易稽核為準 |
| 高 | UI 每次點擊下單都產生新 key，連線不確定後重點可能再建一筆單 | 同一次使用者下單意圖保留 key；提供查詢結果或以同 key 重試的流程 |
| 中 | 頁面只有三個操作及原始 JSON，模式與比較結果分散在 CLI/離線頁 | 增加目前模式、服務狀態、結果入口及失敗原因，保留技術明細供展開 |
| 中 | README 原生與容器路徑、三種後端模式與 Envoy 模式容易混淆 | 建立單一預檢入口及固定操作順序；讓陌生成員完成啟動、重跑、核對、停止 |
| 中 | 單機、單程序狀態，沒有可見的外部使用者驗證 | 若走工具產品路線，先找一個真實服務及操作者驗證接入成本與使用價值 |

健康與下單問題分別由 [health handler](../local_ddos_lab/server.py)、[Compose](../compose.yaml) 及 [前端事件處理](../local_ddos_lab/index.html) 確認。重複訂單是「已提交但回應遺失後，使用者重新點擊」的可能流程，不代表已在本次實驗觀察到重複扣庫存。

後端取消與交易處理值得保留。資料庫工作真正完成才歸還名額，並且有冪等與逐商品稽核，比單純看 HTTP 200 更有研究價值。這也提高了新控制器的舉證責任：既有正確取消、SQL 期限和有限並行若已解決問題，就不應為了題目保留複雜元件。

RLS 也有明確成本：遙測失效超過兩秒會退回基準速率；若此前降到 0.5/s，會回升至 2/s。另一方面 RLS RPC 故障會讓受控 API 回 503。這是既定取捨，尚無本次完整故障注入結果，應量化其對訂單完成率的影響。來源：[stale fallback](../rls/policy.py)、[Envoy RLS 設定](../deploy/render_envoy.py)。

## 是否繼續投入

| 目標 | 判斷 | 原因 |
|---|---|---|
| 大學專題與工程作品 | 有條件繼續 | 交易、取消生命週期、對照工具與原始證據已有基礎；仍需把研究問題收斂 |
| 新演算法或研究發表 | 先驗證再承諾 | 尚無優於簡單方法的效果，也未證明取消訊號的獨立貢獻 |
| 對外防護產品 | 暫不建議按現範圍投入 | 通用性、外部需求、接入負擔與營運可靠性尚無可見證據 |
| 可重播過載與取消觀測工具 | 可作轉向選項 | 能延用既有交易稽核與重現資產；是否值得產品化仍需使用者驗證 |

建議題名先用「應用層過載與取消行為的可重現評估」，保留後端回饋作一個待驗證方法。若課程明確要求新演算法，應提早確認接受何種貢獻，避免直到報告期才發現研究定位不符。

兩週是建議的資源上限，不是已排程的自動任務；以下門檻也只是建議起點，須在看驗證結果前固定：

1. **第 1～3 天確認問題存在。** 在自有隔離環境與共同安全限制下，校準合理 SQL 成本與工作重疊，讓訂單確實遇到資源競爭。同步量測 HTTP、DB 工作、排隊、正常報表及訂單稽核。不能關閉正確取消或只削弱比較組來製造問題。找不到實際損害，就停止「取消殘留防護」這條假說。
2. **第 4～7 天挑戰控制器必要性。** 先比較校準過的 Envoy、固定 RLS、後端固定報表並行額度與 feedback；以獨立組別區分准入策略。測報表成本變動及訂單本身過載。若回饋有收益，再移除取消訊號，檢查新增訊號是否必要。
3. **第 8～10 個工作天做未調參驗證。** 使用平衡順序、固定暖機、未參與調參的種子及到達相位，對關鍵情境至少做 10 次配對重播，報告每次差值與變動範圍；這個次數不自動保證統計力。再由另一位成員或第二台機器重現。

可預先採用的實務門檻範例：在相同資源、工作語意與零稽核錯誤下，feedback 相對最強且事前校準的簡單基準，正常訂單準時完成率提高至少 5 個百分點，同時正常報表完成數至少保留該基準的 90%，且配對結果穩定。5 個百分點與 90% 不是產業標準，應依專題目標調整；若改善只來自更多拒絕，應呈現服務取捨，不能宣稱全面更好。

符合改善門檻才保留策略主線。若取消訊號消融後結果不變，刪除取消特化主張；若簡單基準效果相當，優先採用簡單方法。若兩週後仍無影響或增益，轉向測試／觀測平台；若也沒有外部使用需求，就以完整工程成果結案。

## 踩過的坑

- 工程測試通過不等於研究假說成立；HTTP 成功也不等於訂單與庫存一致。
- 所有組別已達 100% 時，無法證明再提高完成率；低負載的小幅延遲差異不能代替過載收益。
- 名稱叫 feedback 不代表本次有調速，須核對控制日誌。
- 取消探針若沒有讓訂單與報表競爭同一資源，就沒有測到所宣稱的保護情境。
- 觀察後清理時間不等於完整取消成本；離散快照可能漏掉短暫占用。
- 不應把正常報表的犧牲藏在訂單平均改善之下，也不能把不同功能的優先度當成不同使用者的公平性。
- 本機目前不是 Git repository，雖已有來源雜湊，團隊接續工作仍應建立版本管理，明確區分程式主本與 artifacts 的分享副本。

## 可複用的模式

- 先證明問題，再證明方法，最後證明新增元件比簡單方案值得。
- 以「訂單準時且正確完成」搭配「其他正常服務損失」評估，避免只優化單一漂亮數字。
- 把停止條件前移；負結果可以淘汰假說，無須丟棄可重用的測試平台。
- 使用生命週期事件、版本／設定來源與逐筆業務稽核，建立可追溯的實驗證據。
- 用陌生操作者完成一次端到端流程，判斷可用性；功能數量與容器綠燈都不能代替此驗證。
