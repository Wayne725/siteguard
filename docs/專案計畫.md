# 專案計畫

日期：2026-10-01

## 題目與成果

暫定題目：「結合後端工作生命週期回饋之應用層資源防護」。16 週、3～5 人；Python 為主要實作語言，沿用 Envoy，示範網站僅做瀏覽、下單與報表。

核心交付是可重播的實驗、Python RLS 擴充、交易正確性證據與策略取捨。將「取消後殘留工作有沒有影響」作為研究問題，尚未把它定義為 Envoy 漏洞。若問題不存在或改良無效，應如實報告，改以測試方法／觀測工具與失效邊界為成果，不補上 AI 名稱來製造新穎性。

## 第一版結果對後續工作的影響

2026-10-01 已跑通五組容器比較。正常訂單均為 26/26；限流組正常報表僅 2/7、1/7，其他組為 7/7。feedback 速率本輪維持 2／秒，未實際調整。這表示目前首先要校準工作成本與公平比較條件，不能直接宣布回饋機制有效。

下一步依序處理：在所有組別相同的資源下校準可重現壅塞；調整並凍結合理的固定 baseline；衡量正常報表犧牲；再測試回饋是否觸發與帶來收益。若取消後殘留短於輪詢間隔，應研究窗口內累積工作時間的訊號，不以取消次數代替真實資源成本。獨立種子驗證仍保留在後續里程碑。

## 里程碑

| 週次 | 具體工作 | 驗收與決策 |
|---|---|---|
| 1–2 | 跑通原生與容器、交易／取消測試、固定版本與資源、初步對照 | 每人能解釋請求在哪裡排隊，成功訂單與庫存對得上；不能宣稱策略有效 |
| 3–4 | 在自有隔離機器重現混合工作壅塞與取消，量測 HTTP／DB 生命周期 | 至少兩台機器可重播；若只有原型 Bug，所有比較組先修正再測 |
| 5–6 | 校準 Envoy 與固定限流、建立慢取消與輕量取消控制組 | 有獨立正常流量基準，基準不故意設弱；無可重現問題則停止原假說 |
| 7–8 | 改進回饋策略，考慮時間窗、採樣間隔與恢復條件 | 比較吞吐、正常訂單及報表；寫出改善時也會犧牲什麼 |
| 9–10 | 消融：移除取消訊號、僅占用、僅排隊、固定額度；必要時補 per-session 公平性 | 證明新增訊號真的有用；優先功能遭額外需求時須呈現失敗邊界 |
| 11–12 | 凍結參數，保留未調參種子，重複四場景＋兩種取消實驗 | 保存全部原始資料、漏送、版本、資源與順序；報告變動範圍，不只挑最好一次 |
| 13–14 | 第二部自有機器重現；故障情境、過期訊號、RLS 中斷與恢復 | 訂單仍正確；說清楚 fallback、額外延遲與單點限制 |
| 15–16 | 最小展示、整理程式、研究報告、操作手冊與錄影 | 新同學可依 README 啟動、重跑、核對結果；演示不依賴外部攻擊目標 |

## 必須比較的組別

共同條件：app 內部 mode=off、4 DB 工作、24 在途上限、有限排隊、SQL 期限、正確取消、相同資料與資源。

1. 共同硬上限，無額外策略。
2. 原版 Envoy adaptive。
3. 原版 Envoy adaptive＋RLS bypass，估計額外 RPC 成本。
4. 原版 Envoy adaptive＋固定 RLS。
5. 原版 Envoy adaptive＋後端回饋 RLS。

初版工具以短測試順序跑完這些組別。正式研究必須隨機化／平衡組別順序、校準暖機，並加入獨立的固定 RLS 與回饋 RLS 組，判斷兩個控制器互相作用的影響。

既有起始包三種後端並行限制仍保留，但它們與 RLS 速率限制的單位不同，結果不混為同一個算法。

## 分工

| 人員 | 主責 | 交付 |
|---|---|---|
| A | API、交易、PostgreSQL、正確取消 | DB 核對與實際工作生命周期 |
| B | Envoy、容器、資源與量測 | 固定環境、入口隔離、原版 baseline |
| C | RLS、策略與消融 | 假說、可測核心與失敗案例 |
| D | 負載、重現、結果統計 | 同時程、獨立種子、原始紀錄與圖表 |
| E | 整合、最小頁面、文件／展示 | 一鍵實驗、驗收清單與報告 |

若只有三人，A 兼 E、B 兼環境重現、C 兼 D；每次里程碑由另一位組員重跑，避免只有作者能操作。

## 功能範圍

第一階段已選定：真實資料庫工作、共用安全上限、Envoy baseline、Python RLS、取消探針、訂單稽核、離線報表。

後續按實驗缺口新增：Prometheus 指標、PostgreSQL 連線池、按已驗證 session 的公平配額、過載時報表快取／降級、兩台自有主機重播。每新增一項都要有獨立對照，避免無法說明效果來源。

AI 分類、完整電商、公開流量壓測、網路層大流量清洗、多節點全域配額均不列入本次必交。這些功能會擴大驗證範圍，需另立里程碑。

## 可主張與不可主張

可以主張實作了特定後端回饋策略、可重現觀測方法、交易正確的比較平台。只有數據支持時，才在明確場景和資源條件下主張改善。

不能把 token bucket、自動調整、分功能優先或一般取消處理當成首次發明；不能把單機實驗當成真實網路 DDoS 清洗能力，也不能以拒絕更多正常報表換得的訂單改善宣稱全面優越。
