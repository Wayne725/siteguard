## 最後版本的取消觀察

報表探針每秒 2 筆、正常訂單每秒 1 筆、各 5 秒；比較完整等待與連線建立後 50 ms 取消。兩輪共用相同時程，之間等待工作全部結束並重設。正常訂單兩輪都是 5/5，訂單稽核通過且無漏送。

- 10 次報表取消，後端觀察到 10 次斷線及其後的 DB worker 結束。
- 觀察到的最長後續清理時間 **2.073 ms**，不是已證明的嚴重殘留或漏洞。
- 輕量商品探針各 3 秒，在 50 ms 前已完成所有請求，取消未觸發；結果為 `not_observed`，不能用它宣稱已驗證惡意取消的全部情境。
- GET 的 client／server ID 未逐筆連接，分類是在獨立 run 內依 kind 觀測；斷線／工作結束則用後端同一 event ID 配對。
- 清理時間的起點是後端每約 20 ms 檢查時**觀察到斷線**，不是客戶端關閉 socket 的精確時刻，因此未包含發現斷線前的時間。250 ms 間隔的 RLS 輪詢也可能完全漏取這種短暫殘留；不能據此主張已量到完整取消成本。

原始紀錄在 `cancellation-20261001-095028-1fbbbf2e/` 與 `cancellation-20261001-095043-271092b1/`，位於 `local_ddos_lab/results/`。

## 程式檢查

- 原生 unittest discovery：38 項，其中 33 項通過、5 項 PostgreSQL 專用測試另於隔離資料庫實跑並全部通過。
- RLS／Envoy 設定／比較編排器：35 項，其中 34 項通過、1 項 socket 測試在一般環境跳過。
- 該 socket 測試另以真實 localhost gRPC 執行，通過。
- 最後版 HTTP 驗收 11 項通過，包含商品、報表、管理權限、重複訂單、衝突拒絕與精確庫存扣減。
- Envoy 四份 YAML 通過官方 protobuf 型別解析，並全部通過 **v1.39.1 binary 的 `--mode validate`**；不存在的設定檔也確實回傳失敗，版本輸出已核對。

以上為 73 個不同的程式／介面測試案例全部通過；另有原生 HTTP 11 項與容器入口 HTTP 13 項驗收。一般 discovery 中的 skip 由指定環境另跑，沒有當作已通過來計算。

沒有把使用共同 stub 的測試算作真實資料庫壓力測試。生命周期測試刻意控制 worker 結束順序，以驗證取消後不提前歸還名額；實際業務報表使用 SQL，沒有 `sleep()` 模擬工作。

## 容器驗證狀態

已實際建置並啟動 Envoy、FastAPI、RLS、PostgreSQL 四個服務，健康檢查通過。VM 為 Colima 0.10.3、2 vCPU／3 GiB；Docker server 29.5.2。映像固定到 `deploy/image-pins.json` 的官方 registry digest。

PostgreSQL 五項真實交易測試通過，包括同一 key 四次並行下單只扣一次庫存、key 商品衝突回滾、不存在商品不建單、執行前取消不建單、真實 SQL checksum。

透過 `127.0.0.1:8080` 的 13 項 HTTP 驗收通過，包含真實商品／報表／下單、冪等、精確庫存、8080 阻擋管理路徑，以及超過 16 KiB 的 body 回傳 413。原始結果在 `artifacts/verification/postgres-tests.log` 與 `gateway-http.json`。

實跑修正了一個部署問題：僅加入 internal bridge 的容器沒有真正發布主機埠。app／Envoy 改同時加入 `edge` bridge 並保持 localhost 綁定；PostgreSQL／RLS 保留 internal 網路且不發布主機埠。靜態測試也補上這個網路條件。

五組 30 秒、mixed、seed=42 的比較已完成；全部使用 PostgreSQL 17.11、同一時程與資源限制，app 內部 mode=off。原始紀錄、各組 manifest、代理統計、RLS 日誌與 HTML 位於 `artifacts/comparison-20261001-101429-473000/`。

| 組別 | 正常訂單期限內完成 | 成功訂單 p95 | 正常報表完成 | 漏送／訂單稽核 |
|---|---|---|---|---|
| 共同硬上限 | 26/26 | 32.641 ms | 7/7 | 0／通過 |

**沒有證明自訂方法優於原版。** 訂單期限為 1000 ms，所有組別已全部準時完成；新增限制大幅降低正常報表完成數。兩個 RLS 限制組的基準報表速率都是每秒 2 筆，尚未校準。

檢查 RLS 控制日誌後，feedback 在本輪**始終維持 2.0／秒，未觸發縮限或實際調速**。因此 1/7 與 2/7 的差異不能歸因於動態演算法，單次時序波動與小樣本不足以做這種推論。p95 的幾毫秒差別也不構成優越性證據。

本編排器以固定順序做整合 smoke，尚未完成正式暖機、隨機化順序、重複種子與變動範圍分析。可確認五組路徑均運作、RLS 能拒絕、原始資料可保存且訂單一致；不能確認方法的研究貢獻。

最後補測 Envoy adaptive＋PostgreSQL 的相同取消探針：報表 10 次取消均被後端觀察到，觀察後最長清理時間 **3.858 ms**，兩輪正常訂單各 5/5；輕量商品請求全部在 50 ms 前完成，取消未觸發，兩輪訂單各 3/3。全部稽核通過、無漏送。原始資料為 `local_ddos_lab/results/cancellation-20261001-102014-7552bc69/` 與 `cancellation-20261001-102029-541e0773/`。仍未證明存在具有實際影響的取消殘留問題。

目前本機展示維持 Envoy 原版 adaptive、RLS bypass；這是本輪沒有犧牲正常報表的展示設定。參數與策略可由比較腳本切換，管理 token 保留在本機 runtime，未放入結果檔或分享包。

## 限制與下一個驗收

目前不具備真實多來源 DDoS、頻寬清洗、多節點配額或產品等級的可用性。RLS feedback 是可測原型；原生三模式測試沒有經過 Envoy，不能用來推論 RLS 的效果。

下一階段先在相同資源限制下跑完 Envoy 原版、RLS bypass、固定速率與回饋速率，再研究重複種子、控制器互相影響與觀測訊號的消融。應先固定暖機、負載、SLO 與參數，再看結果。
