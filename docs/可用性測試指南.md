# 可用性測試指南

日期：2026-10-03  
適用：SiteGuard 0.3.0、完整原始專案、macOS／Colima。

要判斷可用性，分別驗證能否安裝、正常網站能否使用、防護是否正確、效能代價與故障回復。`check` 通過、容器 ready、HTTP 200 或一個總 passed，都不能單獨代表可上線。

## 通過條件

| 面向 | 應做的測試 | 判定 |
|---|---|---|
| 程式正確性 | 政策、CLI、HTTP 測試工具回歸 | 不接受 failure；逐一檢查 skipped。 |
| 正常使用 | HTML、登入狀態、表單、API、上傳、SSE、WebSocket | 合法操作完整完成；上傳內容不變，交易不重送。 |
| 防火牆 | 允許來源、封鎖來源、重疊規則、IPv4/IPv6、假 XFF | 被封鎖者未到原站；允許者未被誤擋；deny 優先。 |
| 洩漏防護 | 指定 guard 路由回傳假私鑰／token | 客戶端完整回應沒有測試秘密；正常小型 API 仍成功。 |
| 效能 | 同一工作負載比較直連與經過閘道 | 同時看合法請求成功率、p95、誤拒、CPU／記憶體及過載收益。 |
| 維運 | 錯誤規則、來源中斷、檢查程序失效、rollback | 狀態與錯誤可辨識、符合預期拒絕策略、回復後合法請求恢復。 |
| 操作易用性 | 讓未參與開發者只靠文件完成安裝、設定、回復 | 記錄完成率、時間、求助次數及誤操作，不靠作者口頭提示。 |

以下先做有限本機測試。安裝 ZIP 沒有 `tests/` 與開發依賴，請在完整原始專案執行。

## 1. 準備與自動化回歸

以下命令使用同一個終端機。既有 `.venv` 已可用時可跳過建立及安裝步驟。

```sh
cd .
python3 -m venv .venv
.venv/bin/python -m pip install . -r requirements-dev.txt

.venv/bin/python -m unittest discover -s tests/siteguard -v
.venv/bin/python -m unittest discover -s tests -p test_cli.py -v
.venv/bin/python -m unittest discover -s tests/integration -p 'test_*.py' -v
```

需要 Python 3.11+；Node 測試另需 Node。這三組不啟動 Docker，但 gRPC／HTTP 測試會短暫使用本機 socket。所有命令都須成功，並檢查跳過項目；例如沒有 Node 時不能把該部分算成已驗證。

建立本次結果目錄與操作捷徑：

```sh
sg_report_dir="artifacts/siteguard/usability-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$sg_report_dir"
sg_test() {
  .venv/bin/python -m siteguard --docker-context colima-data-security "$@"
}
```

需要 Docker 及 Compose。此專案已有專用 Colima profile，可先確認並啟動：

```sh
colima list
colima start --profile data-security
docker --context colima-data-security info
```

HTTP 測試使用 18088／18100，防火牆測試使用 18090／18102；fixture 自己管理來源站，埠被占用時應查明來源，不要任意停止其他程序。新範例使用獨立專案名稱 `siteguard-usability-http`／`siteguard-usability-firewall`，不同於先前驗收部署。

Docker Desktop 須把兩組範例的 `host.lima.internal` 改為 `host.docker.internal`，並改用自己的 Docker context；以下原樣命令是 Colima 版本。完整 Linux 主機部署仍需依實際網路另驗。

## 2. 正常網站與故障恢復

```sh
sg_test check --config examples/testing/http.yaml
sg_test up --config examples/testing/http.yaml --output "$sg_report_dir/http-deploy"
sg_test status --output "$sg_report_dir/http-deploy"

.venv/bin/python tests/integration/verify.py \
  --base-url http://127.0.0.1:18088 \
  --fixture-url http://127.0.0.1:18100 \
  --suite functional --own-fixture \
  --output "$sg_report_dir/functional.json"
```

這份設定保留 SSE／WebSocket 路由，並為耗資源路由預留較小容量。`--own-fixture` 自行啟停測試來源站，包含來源回 503／恢復，以及 TCP listener 中斷後恢復。測試結束後來源站會停止；此時再用瀏覽器打閘道看到 503，不能直接推論產品壞了。

檢查每項結果，而非只看程式退出碼：

```sh
.venv/bin/python - "$sg_report_dir/functional.json" <<'PY'
import json
import sys
report = json.load(open(sys.argv[1]))['functional']
print('passed:', report['passed'])
for check in report['checks']:
    print(check['status'], check['name'])
assert report['passed']
assert len(report['checks']) == 17
assert all(check['status'] == 'passed' for check in report['checks'])
PY
```

完整本機情境預期 17 項通過。HTTP/2 需要 `h2`；目前驗證器把 skipped 納入總 passed，所以以上額外逐項檢查是必要的。這裡只驗 cleartext HTTP/2，沒有代表 TLS／ALPN 已通過。

## 3. 防火牆是否真的封鎖，以及能否回復

先用「預設全拒絕，但 observe」設定，合法請求仍應成功：

```sh
sg_test up --config examples/testing/firewall-observe.yaml --output "$sg_report_dir/firewall-deploy"
.venv/bin/python tests/integration/verify_firewall.py \
  --phase observe --own-fixture --output "$sg_report_dir/firewall-observe.json"
sg_test metrics --output "$sg_report_dir/firewall-deploy" --format prometheus
```

預期 5 項通過，並有影子拒絕計數。再部署相同規則的 enforce：

```sh
sg_test up --config examples/testing/firewall-enforce.yaml --output "$sg_report_dir/firewall-deploy"
.venv/bin/python tests/integration/verify_firewall.py \
  --phase deny-all --own-fixture --output "$sg_report_dir/firewall-enforce.json"
```

預期 10 項通過：普通請求、SSE、WebSocket 握手與偽造來源標頭都無法到達原站。一般封鎖回 403；`OPTIONS *` 可能因無路由回 404，但必須沒有來源呼叫。這個全拒絕測試只是最短實際封鎖驗證，不能取代完整 IP 白名單、deny 優先與雙棧矩陣。

接著驗證回復前一個成功部署：

```sh
sg_test rollback --output "$sg_report_dir/firewall-deploy"
.venv/bin/python tests/integration/verify_firewall.py \
  --phase observe --own-fixture --output "$sg_report_dir/firewall-rollback.json"
```

預期恢復為前一份 observe，5 項再次通過。rollback 至少需要兩份成功部署，而且不修改來源 YAML；不要立即對 enforce YAML 再執行 up，否則又會啟用全拒絕。

真實來源白名單測試應從兩個受控來源發送請求，搭配原站呼叫紀錄核對。只修改 X-Forwarded-For 是偽造測試，不等於建立第二個真實來源。更完整矩陣與歷史證據見 [網站入口防火牆](網站入口防火牆.md)。

回應洩漏檢查需另用明確啟用 `response_guard` 的專用小型 API、fake secrets 及對應 verifier；不得拿上述關閉一般 security 的防火牆 profile 來宣稱 DLP 測試通過。詳見 [資安防護功能](資安防護功能.md) 與 [整合測試說明](../tests/integration/README.md)。

## 4. 是否拖慢網站，過載時是否有幫助

保留第 2 步 HTTP 部署，先測正常負載：

```sh
.venv/bin/python tests/integration/verify_normal_load.py \
  --output "$sg_report_dir/normal-load.json"
```

目前是每條路徑 40 筆、每秒 20 筆的本機 echo 樣本。兩組應都是 40／40 成功；比較 `summary.direct.p95_ms` 與 `summary.gateway.p95_ms`，不要把這 40 筆延遲外推為生產承諾。

再跑兩種順序的有限過載比較：

```sh
.venv/bin/python tests/integration/verify.py \
  --suite load --seconds 6 --seed 42 --own-fixture \
  --output "$sg_report_dir/load-direct-first.json"
.venv/bin/python tests/integration/verify.py \
  --suite load --seconds 6 --seed 42 --gateway-first --own-fixture \
  --output "$sg_report_dir/load-gateway-first.json"
```

先檢查 `load.valid_comparison` 為 true；再看兩組 `generator_drops`、`audit_ok`、`duplicate_post_attempts`、`on_time_orders`、`order_completion_rate` 與 `order_gain_percentage_points`。重播失效、漏送或重複提交不能當成有效改善；exit code 0 只代表比較有效，不代表有收益，仍須看 `business_benefit_observed`。

若兩個順序都沒有改善，保留結果，檢查容量與適用情境，不要調整測試直到一定贏。上述工具只允許自有 localhost fixture，並非任意網站壓測工具。

## 5. 接到自己的測試網站

本機通過後，用真實網站的測試環境，依序做直連、observe、enforce 三組相同操作：

- 登入／登出、Cookie、權限、表單、搜尋及實際 API。
- 測試訂單／回呼的成功率、唯一提交與冪等性；不要用真實付費交易驗收。
- 常見及界限大小的上傳／下載、SSE 首段、WebSocket 重連。
- 合法管理者、被封鎖來源、NAT 共用出口、CDN／代理來源辨識。
- 被套用 response_guard 的正常回應、假的敏感回應及 scanner 故障時的影響。
- 保留同一資料量、流量模型與測試機資源，記錄 p95、錯誤率、誤拒與 CPU／記憶體。

先訂自己網站的成功率與延遲預算，再比較結果。交易遺失／重複、機密通過、合法使用者無法完成核心流程，都應阻擋上線。錯誤率與延遲的容忍範圍依網站需求決定，不存在本工具通用的安全百分比。

操作易用性可以找 3 位未參與開發的人，各自只看文件完成安裝、加一條封鎖、定位一個錯誤及 rollback；記錄成功率、完成時間、求助次數。這是小樣本找問題，不是統計認證。

## 清理

```sh
sg_test down --output "$sg_report_dir/firewall-deploy"
sg_test down --output "$sg_report_dir/http-deploy"
docker --context colima-data-security ps
```

來源 fixture 已由 `--own-fixture` 清理。只有在 Colima 原本為停止狀態、是本次啟動，且沒有其他容器需要它時，才執行 `colima stop --profile data-security`。保留結果 JSON 供比較；下一輪使用新的結果目錄，避免覆寫。
