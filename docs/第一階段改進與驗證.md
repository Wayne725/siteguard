# 第一階段改進與驗證

日期：2026-10-01

關聯：[[改進執行方案]]、[[專案可行性評估]]、[[測試操作指南]]、[[_索引]]。

## 問題描述

原先實驗缺少逐筆事件證據、簡單的後端固定限制基準與公平配對；健康檢查不能反映資料庫故障，前端重試也可能建立新訂單。本次完成第一階段修正，保留原有回饋演算法，先確認量測與操作可信。

## 解法思路

- **可重播時程**：保留 periodic，加入 jittered、burst；同 seed／參數產生同一份排程，不增加請求總數或既有硬上限。
- **逐筆證據**：用不含業務標籤的 request ID 對應事件，保存排隊、DB 執行、斷線觀察、結束及最終狀態。缺失、重複或截斷時標記不完整。
- **六組編排**：加入後端固定報表並行額度；明記 Envoy／RLS／app mode、來源雜湊、容器與主機資源。支援不同 seed 的配對重複、組別輪轉及 wait/cancel 順序交替，執行中程式變動會中止比較。
- **報告判讀**：普通與取消實驗均可讀取；條件相符才配對，列出正常報表代價、入口拒絕及調速軌跡。基準沒有訂單損害或 feedback 未調速時明確提示，不自動選勝者。
- **操作正確性**：區分 `/live` 與具期限、最多快取 5 秒的 DB readiness；操作頁顯示模式。同一待確認訂單保存同鍵與商品，成功後才建立下一筆；舊 run 的訂單在重設後被拒絕。

### 驗收

112 項 Python 測試及 4 項 Node.js 前端流程測試全部通過。一般 Python 執行先跳過 5 項 PostgreSQL 與 1 項 socket 測試，之後已分別在專用 Compose DB 與真實 loopback gRPC 補跑通過；總數未重複計算。

另完成 18 項 8080 HTTP 驗收，涵蓋真實 SQL／交易、重複扣庫存保護、跨 run 重試拒絕、管理路徑隔離與 body 上限。實際停用專用 PostgreSQL 時 `/health=503`、`/live=200`，恢復後 `/health=200`。紀錄保存在 `artifacts/verification-v2/`。

回應遺失後同鍵重試及舊 run 拒絕，已由 API 整合與前端點擊流程測試覆蓋；尚未安排未參與開發者的操作觀察。HTML 報告完成資料／連結與產生器核對，未完成瀏覽器視覺驗收。

### 同版本普通比較

使用 PostgreSQL、mixed、30 秒、seed 42、jittered，六組各 228 筆預定請求。所有請求均送出，零 drops、訂單稽核通過，事件證據完整。五個策略組均唯一配對 gateway-off，來源與資源一致。

| 組別 | 正常訂單準時 | 正常報表完成 | 訂單 p95 ms | DB 訂單／報表重疊 ms | worker 峰值 |
|---|---:|---:|---:|---:|---:|
| gateway-off | 26/26 | 7/7 | 86.794 | 315.653 | 4 |
| envoy-adaptive | 26/26 | 7/7 | 47.963 | 288.115 | 4 |
| adaptive-rls-bypass | 26/26 | 7/7 | 117.764 | 245.736 | 4 |
| adaptive-rls-fixed | 26/26 | 1/7 | 25.992 | 39.903 | 2 |
| adaptive-rls-feedback | 26/26 | 2/7 | 25.858 | 71.552 | 2 |
| backend-fixed | 26/26 | 5/7 | 23.797 | 220.609 | 3 |

訂單、報表與訂單 p95 採 load phase 的正常請求；重疊與峰值採整輪事件，包含暖機與恢復。基準曾占滿 4 個 worker，共 1741.164 ms，整輪最大排隊 154.856 ms，但訂單仍全數準時。Envoy adaptive 的一筆 503 是額外報表請求，原因為閘道並行限制，並非正常訂單失敗。

feedback 實際調速為零，兩筆更新皆為 2.0→2.0／秒。其報表多成功一筆不能歸因於動態控制；限制組較低的訂單延遲也伴隨正常報表損失。**本輪證明量測可用，沒有證明複雜策略值得。**

原始資料及報告：`artifacts/comparison-20261001-114011-526000/`。較早的 `comparison-20261001-113449-296000` 為開發中整合檢查，第一組與其餘組來源不同，保留原始資料但不作同版本結論。

### 取消比較

六組各跑 wait/cancel，每個 round 5 秒、seed 42、burst、報表工作量 40、50 ms 取消期限。每 round 為 5 筆正常訂單與 10 筆報表探針；12 round 共 60/60 訂單準時，零 drops、全部稽核通過、事件完整。10 個策略 round 分別配對相應的 gateway-off round。

| 組別 | cancel 觀察到斷線 | 觀察後殘留總計 ms | 單筆最長 ms |
|---|---:|---:|---:|
| gateway-off | 10 | 30.937 | 5.393 |
| envoy-adaptive | 10 | 33.155 | 9.989 |
| adaptive-rls-bypass | 10 | 31.999 | 5.819 |
| adaptive-rls-fixed | 10 | 30.882 | 5.007 |
| adaptive-rls-feedback | 10 | 27.080 | 3.624 |
| backend-fixed | 10 | 27.478 | 4.945 |

每 round 都有 5 筆訂單與報表重疊，但 worker 峰值僅 2，未達容量。wait 的探針全部成功；cancel 的 60 次取消全部被觀察到。殘留只從伺服器觀察斷線起算，不能當作完整取消成本。本情境沒有正常報表樣本，不能估計正常報表保留率。

本輪皆 wait-first；wait/cancel 共用 Envoy 控制器，每輪的兩筆暖機不保證完成控制器初始化。已保存各 round 起迄代理統計，報告明示限制；單次數字與兩輪差異不能當作策略優勢或取消的因果效果。原始資料：`artifacts/comparison-20261001-114457-138000/`。

## 關鍵程式碼

先預覽配對條件，再執行：

```bash
.venv/bin/python scripts/run_comparison.py --docker-context colima-data-security --scenario mixed --seconds 30 --seed 42 --arrival jittered --plan
.venv/bin/python scripts/run_comparison.py --docker-context colima-data-security --scenario mixed --seconds 30 --seed 42 --arrival jittered
.venv/bin/python scripts/run_comparison.py --docker-context colima-data-security --workload cancellation --seconds 5 --seed 42 --arrival burst --repeats 2
```

第三行為後續交替 wait/cancel 順序的重播指令；本次取消驗收只跑一輪，不將指令存在視為已完成兩輪。

## 踩過的坑

- localhost 在受限執行環境無法連線，不能推論容器未啟動；實際驗收需有本機 socket 存取權。
- 來源變動會讓表面相同的組別不再可比；以固定版本重跑，舊批資料保留但不混配。
- 入口已拒絕的請求沒有 origin 事件屬正常；證據完整性需與 HTTP 結果一起判斷。
- `complete` 只表示事件足夠，重疊及占滿容量也不等同訂單服務損害。
- 共用控制器狀態與不足暖機仍是正式取消因果研究的缺口，不能靠報告欄位消除。

## 可複用的模式

把工作拆成可重播輸入、真實生命週期、相容條件配對、業務結果與明確限制。先讓錯誤結論難以產生，再考慮增加控制器複雜度。

目前保留 Envoy adaptive、RLS bypass、app off 作本機展示。下一步是定義代表性業務負載、固定暖機與參數後做未調參重複驗證；仍找不到訂單損害或額外收益時，停止取消特化策略，保留此評估工具。
