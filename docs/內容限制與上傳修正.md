# 內容限制與上傳修正

日期：2026-10-01

## 問題描述

執行模式設定 1024 bytes 時，一次送完的 HTTP/1、HTTP/2 請求可能讓 1025 bytes 通過。只調整 filter 順序後，HTTP/1 恢復正確，HTTP/2 單 DATA frame 仍漏擋。另外，等候 `100 Continue` 才送出 body 的客戶端會收到 408。

## 解法思路

普通路由採 `buffer → 固定 Lua 長度檢查 → RLS → router`。buffer 在限流非同步處理前接收內容；Lua 在內容完整後比較實際長度，補足單一末端 DATA frame 的邊界。每個不同上限只生成一份腳本，上限直接來自已驗證整數，不執行使用者提供的程式。觀察模式與明確串流路由同時停用 buffer 和 Lua；WebSocket 保留獨立限流路徑。

`proxy_100_continue` 設 false，由閘道先送出 100，讓客戶端能傳 body；後續內容限制仍照常執行。

## 關鍵程式碼

```lua
function envoy_on_request(handle)
  local body = handle:body()
  if body and body:length() > 1024 then
    handle:respond({[":status"] = "413", ["content-type"] = "text/plain"}, "Payload Too Large")
  end
end
```

1024 是範例；正式程式依每條路由已驗證的上限產生常數。空 body 保留正常語意，沒有字串複製或外部呼叫。

## 踩過的坑

- Envoy buffer 的限制會受 filter manager 的 streaming watermark 狀態影響。單一 `end_stream=true` 資料片段可直接 Continue，不能只依設定格式推論限制已生效。
- 換序只讓 8／10 改成 9／10；不能因大部分案例成功就結案。
- 嘗試 Lua `filterContext()` 時實際未取得上限，腳本例外可能放行。因此改成生成整數常數，並檢查 `lua.errors` 不增加。
- 嚴格 Expect 客戶端必須在收到 100 後才傳 body；一般一次送完的 HTTP 客戶端測不到等待死鎖。

## 可複用的模式

協定限制要在真正的網路邊界測試：HTTP/1 固定長度／chunked、HTTP/2 單／多片段，分別送「恰好上限」與「多 1 byte」。拒絕必須是完整 413，不能把 timeout/reset 算通過。同時核對 upstream 請求計數，確認拒絕沒有到達來源。
