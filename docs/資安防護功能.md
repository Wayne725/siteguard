# 資安防護功能

日期：2026-10-01  
版本：**0.2.0 可受控試用版**。本輪完成 117 項自動化測試、56 項原生資安案例，以及 17 項原有 Python 網站功能回歸。環境為本機 Colima、Envoy 1.39.1 與刻意放入假秘密的隔離來源站；不是第三方網站滲透測試或完整資安認證。

SiteGuard 在既有 HTTP 資源防護上加入四組可設定的資安功能。預設仍是 `mode: observe`，這些請求規則只作影子判斷，**不執行封鎖、不套用回應安全標頭，也不掃描回應內容**；原有協定、逾時與代理基本安全限制仍啟用。僅在設定檔勾選 `response_guard`，不代表已開始阻擋敏感回應。

## 四組功能與適用範圍

| 功能 | 預設設定 | enforce 行為與限制 |
|---|---|---|
| 敏感路徑與 HTTP 方法 | `block_sensitive_paths: true`；`blocked_methods: [TRACE, TRACK, CONNECT]` | 阻擋符合規則的敏感檔案路徑及指定方法。範圍包含 `.env`、版本控制／認證設定目錄、常見私鑰檔名、`wp-config.php`、`web.config` 等有限模式，並非任意機密檔案辨識器。 |
| 路徑來源網段限制 | `protected_paths: []` | 只有來自該路徑允許 CIDR 的請求才放行。重疊路徑必須同時符合各規則，不能由較細規則放寬上層限制。這不是登入、角色授權或 MFA。 |
| 回應安全標頭 | `response_headers: true` | 移除 `Server`、`X-Powered-By`、`X-AspNet-Version`、`X-AspNetMvc-Version`；設定 `X-Content-Type-Options: nosniff`。僅在來源未提供 Referrer-Policy 時加入 `strict-origin-when-cross-origin`，保留既有 referrer 策略。 |
| 指定小型 API 的回應檢查 | 各路由 `response_guard: false` | 僅對明確啟用的普通路由緩衝並檢查回應，辨識有限高可信度私鑰／token 特徵；不支援或檢查失敗的回應拒絕通過。其餘路由不作內容掃描。 |

移除版本標頭只降低直接曝光，不會讓來源服務無法被辨識。以上功能不構成完整 WAF，也不提供通用 SQL 注入、RCE、EDR、惡意程式辨識或所有資料外洩防護；網站仍需維持授權、輸入驗證、秘密管理與更新修補。

## 設定與啟用

下例先使用 observe。文件中的 `203.0.113.10/32` 是示範位址，啟用前須換成實際可由閘道辨識的可信來源；不要為了通過測試把所有網路都加入白名單。

```yaml
version: 1
name: my-site
mode: observe
upstream:
  url: http://host.docker.internal:3000
security:
  block_sensitive_paths: true
  blocked_methods: [TRACE, TRACK, CONNECT]
  response_headers: true
  protected_paths:
    - prefix: /admin
      allowed_cidrs: [203.0.113.10/32]
routes:
  - name: private_api
    prefix: /api/private
    response_guard: true
    max_body_bytes: 16384
trusted_proxy_cidrs: []
trusted_proxy_hops: 0
```

```sh
siteguard check --config siteguard.yaml
```

成功的 `check` 會顯示模式、敏感路徑開關、封鎖方法數、受保護路徑數，以及 `response_guard` 設定數／依該模式實際啟用數。上述範例在 observe 顯示設定 1 條、啟用 0 條，並明示不掃描回應內容。摘要只顯示數量及開關，不列出來源站、管理路徑或 CIDR。

`check` 只讀取本機設定，摘要是「下一次部署將使用的設定」，不能證明正在執行的服務已更新；它也不執行 Envoy 原生驗證或來源探測。確認合法路由、來源 IP 及小型 API 的內容符合限制後，改為 `mode: enforce`，再執行：

```sh
siteguard check --config siteguard.yaml
siteguard up --config siteguard.yaml --output siteguard-deploy
siteguard status --output siteguard-deploy
```

接著實際測試合法請求與預期拒絕案例。`ready` 只表示容器健康，不代表網站業務及每條規則正確。回復到 observe 也需要重新 `up`；正式接入前，仍應在自己的網站驗證合法操作與誤拒代價。安裝、來源網路與既有代理接入詳見 [網站安裝與操作](網站安裝與操作.md)。

設定會拒絕未知欄位及字串形式的布林值。`blocked_methods` 最多 16 個不重複的大寫 RFC token，空清單可停用方法封鎖；`protected_paths` 最多 32 條，每條須有 1～32 個不重複、精確且不是 `/0` 的 CIDR。prefix 必須為 ASCII 絕對路徑，可用 `/`，不得含編碼、空白、分號、查詢、fragment、反斜線、點段、segment 尾端點或重複斜線；尾端斜線會移除，正規化後重複的路徑會被拒絕。

## 來源 IP、可信代理與保守路徑判斷

CIDR 比對使用閘道確認後的來源身分，不能靠用戶端任意填寫 X-Forwarded-For 取得權限。只有確實存在且由你管理的前方代理，才能把其精確網段列入 `trusted_proxy_cidrs`；不要把整個網際網路或所有私有網段列為可信。仍需確保來源網站不能從其他公開入口繞過閘道。

NAT 後多名使用者可能共用出口 IP。允許該 IP 就會允許所有使用此出口的人到達受保護路徑，拒絕也會一併影響他們；IP 白名單不能替代網站登入與逐人授權。加入 CIDR 前，應從實際流量確認看到的是用戶端、NAT、容器網橋還是上游代理位址。

防護規則會保守看待編碼路徑、大小寫、點段、重複斜線、反斜線、分號參數及尾端點／空白，避免應用與閘道對路徑理解不同而漏擋。因此，應用原本視為不同的路徑可能被套用同一限制，無法安全判定的形式也可能遭拒絕。依賴大小寫區別、特殊編碼、原始路徑簽章或矩陣參數的網站須先測相容性；不要以放寬所有管理路徑來消除誤拒。

## response_guard 的硬邊界

此功能只適合**專用小型 API 路由**。`response_guard: true` 必須同時在該路由明確設定 `max_body_bytes`，範圍為 **1～65536 bytes**；不能繼承全站預設，也不能與 `streaming: true` 同時啟用。這個數值是請求與回應共用的硬緩衝上限，不存在獨立的回應大小設定。

guard 路徑亦要求無歧義的 ASCII prefix。canonical 路徑落入 guard 時，若實際選到的路由未掃描或放寬上限，請求會直接遭拒；巢狀 guard 不能放寬父層上限。編碼別名若已由 Envoy 正規化到同一受保護路由，則仍會掃描其回應。

只有 enforce 才啟動內容檢查；observe 不在背景掃描、抽樣或記錄本來會攔截的回應秘密。因此不能靠 observe 的安靜日誌推論「沒有洩漏」。檢查需要先取得完整、大小受限的回應，會增加等待與緩衝成本，不能套用 SSE、WebSocket、gRPC 串流、長下載或大型匯出。

目前接受 UTF-8／ASCII 的文字、JSON 及 `application/*+json` 回應，辨識的秘密模式包括 PEM 私鑰標記及特定 `ghp_`／`glpat` token 格式。比對的是標頭值與 UTF-8 body 的字面特徵，不會遞迴解碼 JSON escape 或 Base64。這不是任意帳密、個資、JWT 或混淆／重新編碼內容的完整偵測。合法提供登入 token、API key、私鑰下載或密碼管理資料的介面不應套用此 guard，否則合法回應也可能被拒絕。

受保護路由會要求來源回傳 identity 編碼並移除 Range／If-Range。若仍收到 gzip 等壓縮內容、binary／不支援的編碼或型態、超過上限、206 部分內容、trailers，會拒絕回應，不會略過檢查後原樣放行。HEAD、204、304 依無 body 語意處理，但標頭仍須符合檢查規則。檢查程序故障、逾時或協定錯誤也採拒絕通過，需評估合法 API 因此無法使用的代價。
