# 網站入口防火牆

日期：2026-10-01

SiteGuard 的防火牆控制經過閘道的 HTTP／HTTPS 請求來源，涵蓋普通路由、SSE 與 WebSocket 握手。它使用 Envoy 原生 RBAC，在讀取請求 body、限流與轉送來源站之前作決定。

## 設定

```yaml
mode: observe
firewall:
  default_action: deny
  allow_cidrs:
    - 203.0.113.0/24
    - 2001:db8:1234::/48
  deny_cidrs:
    - 203.0.113.25
```

以上都是文件示範位址，須改成真正允許進站的來源。單一 IPv4／IPv6 位址會轉成 `/32`／`/128`，也可使用精確 CIDR 網段。每份清單最多 256 筆，不接受 DNS 名稱、重複項目、IPv6 zone ID 或包含 host bits 的網段。

判斷順序：

1. 命中 `deny_cidrs` 就拒絕，即使也在允許網段內。
2. `default_action: deny` 時，只有 `allow_cidrs` 中的來源可繼續；空允許清單代表全站封鎖。
3. `default_action: allow` 時，未被封鎖的來源可繼續。此時必須保持 `allow_cidrs: []`，避免誤以為無作用的清單正在限制來源。
4. 通過防火牆仍須通過敏感路徑、管理路徑、方法、容量與回應檢查等其他規則。

預設為 `default_action: allow`、兩份空清單；舊設定不會突然套用來源封鎖。明確指定 `0.0.0.0/0` 或 `::/0` 會涵蓋相應的整個 IP 家族。IPv4-mapped IPv6（例如 `::ffff:203.0.113.25`）一律視為 IPv4：等價表示法不能繞過封鎖，`::/0` 也不會因此放行 IPv4。

只要封鎖特定來源，可使用：

```yaml
firewall:
  default_action: allow
  deny_cidrs: [198.51.100.23, '2001:db8:dead::/48']
```

## 啟用、檢視與回復

先用 `siteguard check --config siteguard.yaml` 檢查。摘要會顯示預設動作、允許／封鎖數量、封鎖優先，以及空允許清單的全封鎖效果，不列出私有來源明細。

`mode: observe` 只產生影子判斷，不阻擋。完成自己的合法來源測試後改 `mode: enforce`，執行 `siteguard up --config siteguard.yaml --output siteguard-deploy` 才會生效。被拒絕的網站請求回傳 403，來源站不會收到該請求。格式不合法或無對應路由的 HTTP 請求，可能由代理提早回覆其他 4xx，例如 `OPTIONS *` 無匹配路由時回 404，也不會轉送原站。

`siteguard logs` 的 `details`／影子規則會顯示固定識別碼 `firewall_denied_source`、`firewall_default_deny` 或 `firewall_unresolved_source`，`siteguard metrics --format prometheus` 提供各規則的拒絕／影子拒絕計數。

誤封鎖時可從部署主機執行 `siteguard rollback --output siteguard-deploy` 回復前一成功版本，或修改設定後重新 `up`。`check` 只讀本機設定；`status: ready` 只表示容器健康，都不能證明你的合法來源已被允許。

## 來源身分與適用邊界

來源判斷使用閘道確認的 remote IP，任意加上 X-Forwarded-For／X-Real-IP／Forwarded 不會取得白名單權限。前方若有 CDN、負載平衡器或反向代理，必須依實際拓樸設定精確 `trusted_proxy_cidrs`；設定錯誤可能導致將代理或 NAT 出口當作使用者。允許一個 NAT 出口等於允許共用該出口的使用者，仍需網站登入與授權。

防火牆有來源規則且啟用可信代理時，如果連線端與解析出的來源都仍落在可信代理網段，會視為無法確認用戶端並拒絕。這包含 XFF 缺失、格式錯誤、過長或整條鏈只剩可信代理的情況；真實用戶若與代理共用該網段，也可能被拒絕。因此可信網段要精確指定，代理自身的健康探測應有可辨識來源。`trusted_proxy_cidrs` 仍須符合實際連線端的地址家族，不應盲目擴大範圍。

來源站若有可直接存取的公開埠，流量可以繞過閘道。應在部署網路中限制原站入口。規則更新只檢查新的 HTTP 請求／WebSocket 握手，不會撤銷已升級的 WebSocket 或已建立的串流；部署重啟可能中斷連線。

這是網站入口層防火牆，不控制整台主機的 SSH、資料庫埠、UDP、出站連線或其他未經 SiteGuard 的服務，也不負責作業系統補丁、主機惡意程式偵測、通用 SQL 注入／RCE 偵測或頻寬型 DDoS 清洗。

原生規則語意：[Envoy RBAC](https://www.envoyproxy.io/docs/envoy/v1.39.1/api-v3/config/rbac/v3/rbac.proto)、[HTTP RBAC 統計與影子規則](https://www.envoyproxy.io/docs/envoy/v1.39.1/configuration/http/http_filters/rbac_filter)。
