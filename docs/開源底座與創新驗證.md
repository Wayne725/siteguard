# 開源底座與創新驗證

日期：2026-09-30

## 問題描述

16 週、3～5 人的資安專題，沿用 FastAPI 與 PostgreSQL 交易／報表實驗，尋找可延伸的開源架構。功能優先、動態並行、平滑、成本限流已有成熟先例，不能直接宣稱演算法創新。

## 選型結論

採 Envoy 作代理底座，原版 adaptive concurrency 作比較基準；Python 擴充透過官方 Rate Limit Service 的 ShouldRateLimit 介面實作。FastAPI 內保留所有組別共用的資料庫工作硬上限與正確取消處理。

RLS 是一次准入查詢，沒有工作完成通知，因此此介面只管理速率預算，不用它計算資料庫實際在途數。後端工作狀態由 FastAPI 量測。

Netflix concurrency-limits 作演算法參考；APISIX Python runner 的官方 README 仍標為實驗階段；Aperture 功能適合作相關工作，但不把其雲端服務當部署依賴。

## 待驗證的主假說

Envoy v1.39.1 adaptive concurrency 的 onDestroy 會取消尚未完成編碼請求的延遲取樣。這是原碼可確認的設計，尚未證明是缺陷。研究慢請求被取消時，樣本偏差是否使控制器低估後端壓力，以及加入後端占用與伺服器端結果資訊是否能改善。

不能將所有逾時等同於取消：完整回傳的錯誤回應仍可能被採樣。不能假定 HTTP 取消後 SQL 必然繼續執行，也不能把客戶端取消當成可信的過載證據。

## 兩週驗證

1. 固定 Envoy 版本及映像 digest，記錄全部設定，部署 Envoy、FastAPI、PostgreSQL 與監控。
2. 重播正常、報表過載、慢請求取消、輕量請求取消四種有界負載。
3. 分別記錄 HTTP 結束、後端實際工作結束、正常訂單期限內正確完成率、正常報表完成率及控制器名額。
4. 比較原版 adaptive、加固定 RLS 速率限制、加後端回饋 RLS；進一步移除取消相關訊號做消融。
5. 所有版本共用正確取消、交易、有限排隊及資源設定；不得靠修復只有比較組存在的 Bug 製造優勢。
6. 若沒有可重現限制、既有設定即可解決，或新方法只靠更大量拒絕改善，停止將此假說當作創新主線。

## 可交付成果

固定版本基準、重現腳本、Python 擴充、原始紀錄、訂單稽核、消融與失敗案例。只有重現及改良效果成立後才確定研究題名；不預先聲稱全球首創或全面優於 Envoy。
