# 應用層資源防護改進執行方案

日期：2026-10-01

狀態：第一階段程式已實作，包含時程、事件量測、六組編排、報告與操作正確性。實跑與驗收結果見 [[第一階段改進與驗證]]；下文第二批控制器修改及正式重複實驗仍待證據決定。

依 [[專案可行性評估]]，第一階段先改善驗證能力與操作正確性；只有在新證據顯示值得時，才改回饋演算法。關聯：[[原型建置與驗證]]、[[測試操作指南]]、[[_索引]]。

## 問題描述

改進前的比較組正常訂單均為 26/26，feedback 未調速；當時 PostgreSQL 取消探針中的訂單與報表 DB 執行區間沒有重疊。這些結果無法回答「取消是否造成重要壓力、後端回饋能否比簡單策略更好」。因此改進的首要目標是讓實驗能區分方法，而非先讓新方法看起來勝出。

## 解法思路

### 第一批先完成的改動

| 順序 | 修改位置 | 具體改法 | 驗收方式 |
|---|---|---|---|
| 1 | cancellation_probe.py、experiment.py | 保留目前固定時程作舊基準；增加可重播的到達相位／有界突發設定；取消探針開放既有允許範圍內的 report_rounds；先生成並保存排程，再讓所有方法重播同一份 | 同 seed 與設定生成相同排程；不同相位確實改變到達時間；總請求數與安全上限不變；原始事件可以判斷是否重疊、排隊及占滿 worker |
| 2 | cancellation_probe.py、server.py | 用不含正常／額外需求標籤的有界 request ID 關聯客戶端與伺服器事件；保存 DB 開始、觀察斷線、DB 結束；把 DB 執行重疊、排隊及清理時間寫入結果 | 每筆已接受的探針可對應完整事件；資料遺失、ID 衝突或事件截斷時標記證據不足；重疊不自動判定為過載 |
| 3 | scripts/run_comparison.py | 將組別明確記成 Envoy、RLS、app mode 及參數；加入後端固定報表並行額度組；支援取消／等待工作負載、配對重複及平衡或隨機組別順序；wait／cancel 的先後順序也要平衡 | 同一配對的排程雜湊、資料集與資源一致；各組實際模式符合 manifest；種子、順序、暖機與參數可追溯 |
| 4 | summarize_results.py | 在完成率之外加入證據狀態、控制器調速軌跡、排隊／占用、正常報表損失、每輪差值及拒絕原因；接入取消實驗結果，現行程式會略過取消 summary | 基準無服務損害時顯示「未形成可比較的壓力」；feedback 未調速時顯示「未驗證動態控制」；沒有把單次最好結果當結論 |

上述檔案除 scripts/run_comparison.py 外，均位於 local_ddos_lab/。不讓策略讀到測試端的正常／額外需求標籤；用於事件關聯的 ID 也不能參與准入判斷。

調整時程只是增加觀測機會。仍須先定義有代表性的業務工作量，再檢查正常、接近容量、過載三段行為；不能持續改參數直到 feedback 贏，也不能故意關閉正確取消來製造優勢。所有方法共用 SQL 期限、交易語意與硬上限。

### 比較基準先從最少組別開始

保留共同硬上限、Envoy adaptive、adaptive 加 RLS bypass、adaptive 加固定 RLS、adaptive 加 feedback 五組，另外加入「共同硬上限加後端固定報表並行額度」。後端 fixed_limit 已支援 1～3，先用校準資料選定，之後凍結。

原有五組維持 app mode=off；新增後端 fixed 組是明確不同的准入策略，使用同一 PostgreSQL、入口路徑及其他限制。這樣才能回答新增 RLS 是否比後端直接限制報表值得，而不是把只有新方法才有的額外保護混進去。

第一輪如果 feedback 沒有收益，就先停在這裡。若有收益，再增加「feedback 移除取消訊號」的消融組，必要時加入獨立 RLS 組分離 Envoy 與 RLS 的互相影響；不用一開始把全部組合都做完。

### 操作正確性可並行改善

| 修改位置 | 改法 | 驗收方式 |
|---|---|---|
| server.py、database.py、postgres_database.py、compose.yaml | 區分程序存活與業務就緒；就緒檢查使用有期限且低成本的 DB 探測，控制檢查頻率，避免成為額外壓力 | 隔離環境中 DB 不可達時就緒回 503，恢復後回 200；存活仍能獨立辨識；各比較組檢查開銷一致 |
| index.html | 同一次下單意圖保存 request_id 與 product_id；結果不確定時提供同鍵重試，成功後才建立下一個意圖 | 模擬訂單已提交但回應遺失，重試後只有一筆訂單、庫存只扣一次；待確認時不能換商品沿用同鍵 |
| README.md、操作頁 | 統一「檢查環境 → 啟動 → 驗收 → 跑實驗 → 看結果 → 停止」路徑；明示目前後端／代理模式；提供成功與拒絕的可讀訊息 | 由沒寫過程式的組員依文件完成一次流程，記錄卡住的位置；技術細節保留供展開，不只顯示 JSON |

若待確認訂單保存在瀏覽器，還需與實驗 run_id 綁定；實驗 reset 後不可將舊待確認意圖自動重送至新資料集。健康檢查也應避免把密碼、管理 token 或詳細 DB 例外回傳給操作頁。

### 第二批依證據才改控制器

只有在看到持續且有業務影響的壓力後，才修改 rls/policy.py 與 rls/server.py：

1. 若短暫取消殘留被快照漏掉，增加伺服器端累積工作時間計數，回饋端讀取窗口增量。分開統計一般工作占用與斷線後占用，不能用取消次數替代成本。
2. 避免所有壓力都透過減少報表處理；至少區分訂單與報表的占用，並測試訂單本身湧入的失敗邊界。只有路由桶時，不宣稱具備使用者公平性。
3. 比較目前遙測逾期回基準速率的做法，與經校準的保守固定退回策略；將 RLS 中斷、狀態過期與恢復的訂單結果列入成本。

每次只變更一個關鍵因素，保留原版與移除新增訊號的對照。AI 分類、完整電商、多節點共享額度及大幅視覺改版先不列入此階段。

## 關鍵程式碼

以下為建議的驗收計算示意，尚未整合到報告程式。數值是討論用門檻，不是產業標準。

```python
order_gain_pp = 100 * (feedback_order_rate - baseline_order_rate)
report_retention = feedback_completed_reports / baseline_completed_reports

passes_gate = (
    audit_errors == 0
    and generator_drops == 0
    and order_gain_pp >= 5
    and report_retention >= 0.90
)
```

僅在兩組有相同正常請求數、基準正常報表完成數大於零，而且基準確有改善空間時使用上述計算。還需看未調參重複實驗的變動範圍、正常負載是否退步及故障代價；單輪布林值不能代替研究結論。

## 執行順序與停止條件

- 第 1～3 個工作天：完成時程、事件與證據有效性判讀；確認工作真的競爭資源，以及競爭是否造成訂單損害。
- 第 4～6 個工作天：加入簡單基準與配對編排，校準後凍結負載及各方法參數；健康與下單重試可由另一位成員並行處理。
- 第 7～10 個工作天：以未調參種子及不同到達相位重播關鍵情境，建議至少 10 次配對觀察；由另一位成員重現。次數不等於統計力保證。

找不到基準損害，停止取消特化假說；固定限制已達同樣效果，採較簡單方案；只有大量犧牲正常報表才有改善，誠實呈現取捨。若兩週內無法證明額外收益，保留測試與交易稽核平台，轉向可重現的過載／取消評估工具。

## 踩過的坑

- 調整請求相位只是可能產生重疊，不能直接當成測到資源瓶頸。
- 原生 experiment.py 已有 repeats 並會洗牌後端模式；缺口主要在 Compose 五組編排，避免重複實作已有功能。
- 固定基準的參數也要校準，不能保留弱基準，再只替 feedback 調參。
- 狀態探測、額外日誌及暖機都可能改變負載；開銷需一致、邊界需記錄。
- 下單重試必須保留同一個業務意圖的鍵；後端有冪等不代表前端自然安全。

## 可複用的模式

先修量測，再補簡單基準，再用消融證明複雜度值得。把每項改動綁定一個能否證明的問題，以及一個具體驗收，而不是以完成多少功能作進度。
