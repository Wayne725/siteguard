## 建議的首版支援範圍

| 面向 | 首版建議承諾 | 邊界與驗收要求 |
|---|---|---|
| 部署 | 單機、單組 Envoy 與私有限流程序，以 Docker Compose 部署；Python 3.11 以上 CLI | 現有實測來自本機 macOS／Colima。Linux 應完成獨立安裝及網路驗收後列入正式支援；WSL2 尚無本表可核對的實測證據。 |
| 接入 | 一個可由閘道連到的 HTTP／HTTPS 來源站，採路由設定；可保留既有 HTTPS／CDN／反向代理 | 網站無須 SDK 或雲端 API key；Docker 網路、Host、信任代理及來源防繞過必須依現場驗收。 |
| 一般功能 | HTML、HEAD、表單、JSON、Cookie、Authorization、轉址、快取、Range、小型 multipart 上傳 | 僅聲明已測案例；大型上傳、框架中介層、瀏覽器登入與外部支付回呼需另驗。 |
| 串流 | 明確設定 `streaming: true` 的 SSE／WebSocket 路由進入試用 | 目前只有短時 SSE 首段與基本 WebSocket 案例。gRPC 串流、長時間連線、多路複用與斷線重連未完成產品驗收。 |
| 防護 | HTTP 層速率限制、路由資源隔離、普通路由 body／逾時限制 | 下列 body 矩陣已通過；各真站上限與路由仍須驗收。並行額度不是嚴格應用程式 semaphore。 |
| 維運 | 本機設定檢查、候選驗證、部署狀態、日誌、指標、版本回復 | `ready` 只代表代理與限流容器健康；還須實際請求來源站。回復不包含外部憑證與來源站資料。 |

首版不承諾：跨副本共享額度、跨機高可用、全球流量調度、L3／L4 或頻寬耗盡型 DDoS 防護、自動憑證申請續期、網站漏洞防護、交易冪等或資料庫查詢期限。限流程序重啟會重建配額；NAT 共用出口與 IP 記錄額滿時的共享桶可能影響合法訪客。

## body 限制：已通過的 10 案例矩陣

使用 [verify_body_limits.py](../tests/integration/verify_body_limits.py)，在明確配置 `mode: enforce`、普通 `/echo` 路由、上限 1024 bytes 且速率桶足以放行 10 次的測試部署執行。下表每列各送 1024 與 1025 bytes，共 10 案例；不能把與 body 無關的 429 當成功。

| 傳輸 | 1024 bytes | 1025 bytes |
|---|---|---|
| HTTP/1.1，Content-Length，一次寫入 | 200、完整原文回顯 | 完整 HTTP 413 |
| HTTP/1.1，Content-Length，兩次寫入 | 200、完整原文回顯 | 完整 HTTP 413 |
| HTTP/1.1，chunked，兩個 body 區塊 | 200、完整原文回顯 | 完整 HTTP 413 |
| HTTP/2，一個 DATA frame，無 Content-Length | 200、完整原文回顯 | 完整 HTTP 413 |
| HTTP/2，兩個 DATA frames，無 Content-Length | 200、完整原文回顯 | 完整 HTTP 413 |

兩段之間間隔 50 ms；HTTP/2 使用明文 prior knowledge。socket reset、EOF、timeout 都不算有效 413；原始 body hash、回應、傳送事件、協定及錯誤必須保留。路由覆寫上限、`streaming: true` 豁免及觀察模式另有各 7 次的 `route-body` 證據；這些有限案例仍不代表所有協定及容量都已驗證。

## 本機受控負載：已觀察到的效益與代價

以下每組到達窗口 6 秒、24 筆訂單與 96 筆重工作；來源用 4 個共享工人執行 PBKDF2 CPU 工作，非單純 sleep 延遲。300 ms 是此 fixture 自訂的訂單期限，不是網站通用 SLO。每對 direct／gateway 的排程雜湊相同、產生器 drops 為 0、稽核通過，且未見重複合法 POST；這些條件僅支撐表內配對比較。

| 原始證據 | 執行順序 | 準時訂單 direct → gateway | 成功 ACK 訂單 direct → gateway | 重工作 200 direct → gateway | gateway 重工作拒絕 |
|---|---|---|---|---|---|
| [Python seed 42](../artifacts/siteguard/python-integration.json) | direct → gateway | 3／24 → 24／24 | 23／24 → 24／24 | 83／96 → 24／96 | 69 筆 429、3 筆 503 |
| [Node seed 42](../artifacts/siteguard/node-integration.json) | direct → gateway | 3／24 → 24／24 | 22／24 → 24／24 | 83／96 → 24／96 | 69 筆 429、3 筆 503 |
| [Node seed 43](../artifacts/siteguard/node-load-seed43.json) | gateway → direct | 3／24 → 24／24 | 23／24 → 24／24 | 83／96 → 27／96 | 69 筆 429 |
| [Node seed 44](../artifacts/siteguard/node-load-seed44.json) | direct → gateway | 3／24 → 24／24 | 23／24 → 24／24 | 83／96 → 27／96 | 69 筆 429 |
| [Node 修正後 seed 45](../artifacts/siteguard/node-final.json) | gateway → direct | 3／24 → 24／24 | 23／24 → 24／24 | 83／96 → 24／96 | 69 筆 429、3 筆 503 |
| [Python 最終 wheel seed 44](../artifacts/siteguard/python-final.json) | direct → gateway | 3／24 → 24／24 | 21／24 → 24／24 | 84／96 → 25／96 | 69 筆 429、2 筆 503 |
| [Python 最終 wheel seed 43](../artifacts/siteguard/python-load-seed43.json) | gateway → direct | 3／24 → 24／24 | 18／24 → 24／24 | 86／96 → 27／96 | 69 筆 429 |

這些配對的準時訂單率均增加 87.5 個百分點，同時降低重工作完成量。它們證明「這個負載與設定下，保留訂單處理額度有作用」，不能把被拒絕的 `/heavy` 都算成惡意流量，也不能代表真站淨收益。真站重工作可能包含付費報表或合法使用者，必須納入損失。七份短樣本不提供長期可靠性、統計信賴區間或最大可承受流量結論；第二個 HTTP stack 仍是受控測試站。早期樣本與修正後樣本分列，不冒充全部來自同一最終版本。

### 正常低負載的延遲代價

[normal-load.json](../artifacts/siteguard/normal-load.json) 對閒置本機 Python `/echo` 以每秒 20 次、direct／gateway／gateway／direct（ABBA）順序執行，每條路徑各 40 次：

| 路徑 | 成功請求 | p50 | p95 |
|---|---|---|---|
| direct | 40／40 | 1.487 ms | 1.967 ms |
| gateway | 40／40 | 5.625 ms | 7.067 ms |

此樣本沒有錯誤，但 gateway 的 p50 增加 4.138 ms、p95 增加 5.100 ms；因此不能宣稱防護沒有正常流量成本。ABBA 減少固定順序的干擾，仍只有單機、低負載、小型回應與少量觀測，未估計信賴區間，也未覆蓋 TLS、跨網路、大型內容或真站延遲 SLO。

本次可受控試用版安裝包為 `siteguard_gateway-0.1.0-py3-none-any.whl`，SHA-256：

```text

```

```sh
.siteguard-venv/bin/siteguard up --config siteguard.yaml --output siteguard-deploy
.siteguard-venv/bin/siteguard status --output siteguard-deploy
```

`init` 預設 observe 與 `127.0.0.1:8088`。Colima 請換用 `host.lima.internal` 並指定 `--docker-context`；既有容器用私有 Docker 網路接入，細節見 [網站安裝與操作](網站安裝與操作.md)。先檢查設定、請求閘道並驗證原站功能，再切換既有反向代理；本工具不自行修改 DNS。

`check` 與 `render` 可純本機執行，但不代表 Envoy 或來源已就緒。`up` 首次需要下載建置依賴，經原生設定驗證及容器健康檢查；仍須另外做來源端到端探測。部署後用相同 output 執行 `metrics`、`logs`、`up`、`rollback`、`down`。已部署 output 的更新使用 `up`，不要以 `render` 覆寫；不同網站使用不同 `name` 及 output。回復快照不含私鑰內容，也不回復原網站資料。

發布時應一併提供 wheel SHA-256、支援環境、預設設定、安裝／升級／回復步驟、已知限制與本表對應的最終證據。單有 wheel 檔或 CLI 可啟動，不等於所有網站接入與防護效果已獲驗證。
